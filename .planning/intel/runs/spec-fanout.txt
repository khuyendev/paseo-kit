Requirement format (follow the GSD requirements template's spirit; this exact shape):
### <ID> <short title>
- Requirement: one falsifiable statement of what the kit does ("`ph spawn` refuses a name already used by a live subagent of the caller, exit 1, one `failed` line").
- Acceptance: the concrete check that proves it (offline test, command and expected output, file state).
- Source: map behavior IDs, D-NN, INV-NN it comes from.
- Scope: v1 | later.
IDs use four-letter module prefixes, numbered per prefix from 01, so they never collide with the three-letter map IDs: INST (M1 install), MACH (M2 machine), CONF (M3 config), PCLI (M4 paseo-client), PHCL (M5 ph), FLOW (M6 workflow), FTOL (M7 files), HOOK (M8 hooks), GSDC (M9 gsd-core), GSDF (M10 gsd-flows), HARN (M11 harness), ADPT (M12 adapter), PANL (M13 ui). Cross-cutting rules (invariants that span modules) go to the module that enforces them, citing the INV.
One requirement per testable behavior; merge behaviors that are one contract; split a behavior that hides two contracts. Every v1 requirement must be testable offline or by a named manual check. Later-scope items are listed briefly (title, source) without acceptance.
Vanilla (D-110): no project-, engine- or game-specific content; when a mechanism needs project data, the requirement says the adapter supplies it (ADPT requirements define the adapter contract). Skill text (D-111): requirements for the harness and GSD skills say the method text is carried unchanged from its source and name exactly which adapter-layer parts the kit changes; do not specify rewrites of the method.
