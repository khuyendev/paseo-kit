## Summary

The area gives Claude Code three batch file tools (`read_ranges`, `edit_multiple_files`, `write_multiple_files`) plus 14 filesystem-MCP-compatible helpers. In the Claude edition they are not an MCP server: a project-local Claude Code "mod" (TypeScript, sandboxed, no Node imports) registers 17 tools at `session.start`; every call is staged to a trusted one-shot Node backend (`backend.mjs`) through JSON on stdin, the real I/O runs through the native `Bash` tool (`node backend.mjs --plan|--execute <session-hash> <ticket>`) so Claude Code's own permission and hook chain applies, and results come back through private per-session state files in `os.tmpdir()`.

Genuinely valuable and worth keeping in spirit: (1) batch read with per-entry independent errors, line numbers, size/binary limits and "did you mean" path suggestions (born from 346 failed reads in a week); (2) batch edit with partial success, retained fix IDs consumed once, atomic/dryRun, CRLF preservation, already-applied detection and rich near-match diagnostics, which together cut re-sent edit text; (3) line edits keyed by a per-read tag with per-line hashes, which save output tokens and survive earlier edits that moved lines; (4) all-or-nothing multi-file write with rollback; (5) session-bound state so fix IDs and tags never cross sessions; (6) a hard rule that outputs stay below Claude Code's ~50,000-character persistence threshold (pagination at 36,000).

Over-engineered / to simplify: the 3-phase ticket protocol (stage, plan, execute, collect; 5 process hops per call) with pid lock recovery, receipts, abandon, sweep budgets and plan-signature re-check exists only because the mod is sandboxed and the backend is a one-shot process; 14 compat filesystem methods (directory walks, media, reindenting `edit_file`, git-style diff) that native Read/Glob/Grep/Bash already cover; the whole legacy MCP adapter set (`mcp/*`) which the owner dropped. The read limits (200,000/450,000) were tuned for MCP inline output and do not fit the mod's 36,000-character pages.

### FIL-13 Session lock and stale-lock recovery

### FIL-32 Fix IDs: format, retention, single use
- Behavior: IDs are `<RUN><n>`: RUN = 2 random lowercase letters chosen once per session state, n = session counter (so IDs look like `kq12` and line-edit read tags `kqt3`). ## Invariants and lessons

1. A mutation executes at most once. A completed result is never re-run; an unknown outcome is reported as `EXECUTION OUTCOME UNKNOWN` with a recovery path; never "retry blindly". Source: kit:project/.agents/harness/files/backend.mjs:285-287 ; kit:project/.claude/plugins/harness-files/hooks/register.ts:93-108 ; test kit:project/.agents/harness/files/backend.test.mjs:168-181.
2. No tool result may pass Claude Code's ~50,000-character persistence threshold (page at 36,000; mod rejects > 40,000); MCP's `maxResultSizeChars` annotation is not assumed to work on mod tools. Incident: a 24-file `read_multiple_files` returned 6.1 MB and was saved to a file the agent had to re-read (owner 2026-10-08). Source: kit:project/.agents/harness/files/backend.mjs:21,200-213 ; kit:project/.claude/plugins/harness-files/hooks/register.ts:91 ; kit:project/.agents/harness/files/read_limits.mjs:4-6 ; kit:mcp/mcp_fs_proxy.mjs:3-5.
3. Errors are never lost to pagination: error text is paged with its fix IDs, and fix IDs are persisted before paging. Source: kit:project/.agents/harness/files/backend.mjs:205,212 ; kit:project/.agents/harness/files/backend.test.mjs:119-131.
4. Mutation targets are never guessed; read targets may be, only when the guess is unique, inside the cwd root, read-permitted and announced in the output. Source: kit:README.md:95-96 ; kit:project/.agents/harness/files/path_guess.mjs:33 ; kit:project/.agents/harness/files/batch.mjs:418-421.
5. Per-entry independence: a bad path, folder, past-end range, binary or oversized entry fails alone; sibling entries still return. Source: kit:project/.agents/harness/files/batch.mjs:461-493.
6. Edits are partial by default, with retained single-use fix IDs, and a resent edit is skipped, not failed or double-applied (`a`->`a b` must not become `a b b`; a line insert at a read edge must not apply twice). Source: kit:CHANGELOG.md:21 ; kit:project/.agents/harness/files/batch.mjs:156-162,230-240.
7. Changed lines are never edited through a stale tag; the server proves the lines still read as shown (hash window of +-2 context lines) or tells the caller exactly what to resend. Source: kit:CHANGELOG.md:19 ; kit:project/.agents/harness/files/batch.mjs:310-343.
8. Dry runs and aborted/atomic-failed calls leave no trace (no signatures recorded, no IDs consumed). Source: kit:project/.agents/harness/files/batch.mjs:435,448 ; kit:mcp/test_fs_batch.mjs:190-197.
9. Multi-file writes are all-or-nothing with rollback, no stray `.tmp`, and a clear `ROLLBACK INCOMPLETE` report; Windows rename retries on EPERM/EBUSY/EACCES. Source: kit:project/.agents/harness/files/batch.mjs:62-101.
10. State (fix IDs, tags, continuations, receipts) is bound to the Claude session; another session sees `unknown`. Source: kit:project/.agents/harness/files/backend.mjs:233-236 ; kit:project/.agents/harness/files/backend.test.mjs:68-95.
11. Permission checks fail closed; ask is never promoted; the executed target set must equal the checked set (symlink swap rejected); the mod does no target I/O itself; payload never appears in a command line. Source: kit:project/.claude/plugins/harness-files/hooks/register.ts:3,28-33 ; kit:project/.agents/harness/files/backend.mjs:176-184.
12. Project configuration errors fail the call with the loader message and never break tool registration. Source: kit:project/.agents/harness/files/backend.test.mjs:281-288.
13. Relative and Git Bash paths must resolve against the session cwd (208 of 346 failed reads in one week were relative paths). Source: kit:mcp/mcp_fs_proxy.mjs:9-11 ; kit:project/.agents/harness/files/path_guess.mjs:2-4.
14. Text read tools refuse binary files (NUL in first 8,000 bytes) because UTF-8 decoding turns bytes into ~1-token replacement characters. Source: kit:project/.agents/harness/files/read_limits.mjs:6-8,27-38.
15. Edit replies are summaries, not diffs (Markdown spec paragraphs made 5.5k-char diffs, 7.4 M a week). Source: kit:mcp/mcp_fs_proxy.mjs:14-18.
16. Images per turn were capped because 5-7 images in one turn made GPT-family agents fail with API error 400 (context window); the cap lived only in the dropped proxy. Source: kit:mcp/mcp_fs_proxy.mjs:31-35.
17. A process killed mid-operation (Esc, timeout) must never wedge the session lock. Source: kit:project/.agents/harness/files/backend.mjs:57-59 ; kit:project/.agents/harness/files/backend.test.mjs:228-237.
18. Huge single lines must not become huge JS strings (bounded-memory reader). Source: kit:project/.agents/harness/files/read_limits.mjs:56-58 ; kit:project/.agents/harness/files/backend.test.mjs:198-210.
19. Malformed JSON input must be answered, never crash the server (legacy audit SIDE-7); empty oldText must not hang (SIDE-2/3); two entries for one file must both apply (SIDE-4). Source: kit:mcp/mcp_fs_batch.mjs:13-17 ; kit:mcp/test_fs_batch.mjs:69-76.
20. Native Read/Edit/Write remain usable; the mod never impersonates them or their media results. Source: kit:README.md:103-107.

## Interfaces

CLI of the backend (`project/.agents/harness/files/backend.mjs`):
- `node backend.mjs` with JSON on stdin: `{action:'describe'}` -> `{protocol:1, tools:[{name,description,inputSchema,isDeferred}]}`; `{action:'stage', session, cwd, method, args}` -> `{protocol, session:<sha256>, ticket:<64hex>}` or, for continuation/receipt, `{..., continuation:true}`; `{action:'collect', session, ticket, phase?:'plan'|'result'}` -> `{checks:[{tool,input}]}` or `{text,isError}`; `{action:'abandon', session, ticket}` -> `{started:boolean}`. Exit 1 + stderr message on failure.
- `node backend.mjs --plan|--execute <session-sha256> <ticket>`: prints `harness-files ticket completed` on success; exit 1 and stderr otherwise.
Tool surface (shipped candidates): `read_ranges {ranges:[{path,from?,to?}]}`; `write_multiple_files {files:[{path,content}]}`; `edit_multiple_files {files:[{path,tag?,edits:[{oldText?|from,to?|after, newText}]}], fixes:[{id,occurrence?,oldText?,newText?,path?,tag?,from?,to?,after?}], atomic?, dryRun?}`; every tool also takes `continuation` or `receipt`. Registered names `mcp__harness-files__<method>`.
Output formats: `===== <abs> lines F-T of N[, tag T]` + `<n>| text` lines; `ERROR <msg>` lines; failure line `<id> <label>: <why> -> fix: {...}`; result headers `nothing written ...`, `DRY RUN, nothing written ...`, `PARTLY WRITTEN ...`, `edited <abs>: N edit(s), +d chars`; paging line `CONTINUATION <64hex>: call mcp__harness-files__<method> with {"continuation":"<64hex>"} ...`.
Files: private state dir `<tmpdir>/paseo-harness-files-<uid|user>/<sha256 session>/` with `<ticket>.request.json|plan.json|result.json|page.json`, `<ticket>.started`, `state.json` ({run, nextFix, fixes[], nextRead, reads[], written[]}), `session.lock` ({pid}). Plugin files: `.claude/plugins/.claude-plugin/marketplace.json`, `harness-files/.claude-plugin/plugin.json`, `harness-files/hooks/hooks.json` ({modules:[...]}), `hooks/register.ts`. Install record `.agents/harness-kit.json` (version, kit, files{rel: 16-hex digest}).
Config keys (owned by config area, consumed here): `read_limits.fileMaxChars` 200000 (largest rendered text of one read entry), `read_limits.replyMaxChars` 450000 (budget of one read reply), `read_limits.mediaPerTurn` 1, `read_limits.mediaTurnGapMs` 1000; constraint `fileMaxChars <= replyMaxChars < 500000`. Constants in code: PAGE_CHARS 36000, MAX_INPUT 16 MiB, lock wait 20 s, unwritten-lock 10 s, ticket expiry 1 h, budget 64 MiB / 384 files, fix store 500 / 8 MiB, written signatures 2000, read tags 64 / 30000 lines, guess budget 20000 entries / 5 listed, directory walk 20000, transport timeout 30 s, Bash timeout 120 s.
Environment: `PASEO_HARNESS_ROOT` (project root override), `CLAUDE_CONFIG_DIR` (plugin install scope), `CLAUDE_CODE_PLUGIN_DIRS` (not settable from project settings), `ENABLE_TOOL_SEARCH` (harness agents).

## Concerns

1. `~` mismatch: the permission plan expands `~` (kit:project/.agents/harness/files/filesystem.mjs:31 via backend.mjs:112) but the batch tools resolve with `path.resolve(cwd, nativePath(p))` without expansion (kit:project/.agents/harness/files/batch.mjs:57), so `~/x` is checked as the home file but executed as `<cwd>/~/x` and rejected by the guard as unplanned. Appears unverified by any test.
2. Case-insensitive containment on all platforms: `inside()` lower-cases paths and roots even on POSIX (kit:project/.agents/harness/files/batch.mjs:55-58); on Linux this conflates distinct paths (low impact because the allowed roots are filesystem roots, backend.mjs:191-192).
3. The "allowed directories" of the mod path are only the roots of the planned targets, so the sandbox is the permission plan alone (kit:project/.agents/harness/files/backend.mjs:191-192). Fine if intended, but the `path outside allowed directories` text is misleading there.
4. The plan returned to the mod carries full payloads: each Write check's `input.content` and each Edit's `old_string/new_string` (kit:project/.agents/harness/files/backend.mjs:127-129,272). Large writes are echoed through stdout (truncation fails closed, register.ts:23), stored again in `plan.json`, and the comment at backend.mjs:271 ("never expose retained old/newText") is only true for fix state.
5. Every executed call rewrites `state.json` with the whole fix store (up to 8 MiB) and read hashes (up to 30,000 lines) (kit:project/.agents/harness/files/backend.mjs:290 ; batch.mjs:499) and `remember()` re-serialises the whole store per failure (batch.mjs:227): O(n^2) with hundreds of failures (the 600-failure test exists, backend.test.mjs:125).
6. Five process hops plus two permission rounds per call, and `executeRequest` recomputes the whole plan (including directory walks) just to compare signatures (kit:project/.agents/harness/files/backend.mjs:176-178): latency and complexity for the common single-read case.
7. The session lock is held during the whole `--execute` while waiters give up after 20 s (kit:project/.agents/harness/files/backend.mjs:73-84): parallel tool calls in one turn that include a slow operation can fail with `locked by another running file operation`.
8. `commit()` replaces files by rename of a fresh temp: POSIX mode bits (executable), ownership and hard links are not preserved and a symlink target is replaced by a regular file (kit:project/.agents/harness/files/batch.mjs:79-81,90). Rollback rewrites bytes, not metadata (batch.mjs:93). Directories created during staging are not removed on failure (batch.mjs:77).
9. Mixed line endings: any `\r\n` makes the whole file CRLF on write (kit:project/.agents/harness/files/batch.mjs:245,433). Edits of binary files are not rejected and would be decoded as UTF-8 (batch.mjs:244-246).
10. `read_ranges` does not validate `to >= from` (schema only `minimum: 1`, kit:project/.agents/harness/files/batch.mjs:20,479 ; read_limits.mjs:59-61); an inverted range appears to produce an empty entry with a header like `lines 5-3` (not tested).
11. Private session directories are never removed, only their expired files (kit:project/.agents/harness/files/backend.mjs:214-236); `state.json` has no expiry.
12. Comment/code conflicts: path_guess header says matching ignores case but only win32 folds case (path_guess.mjs:5 vs :16); backend.mjs:222 says unfinished tickets are never silently discarded but 1-hour expiry deletes them (backend.mjs:219; the later read does report `unavailable`).
13. Name shadowing and duplicated constants: `const LIMITS = limits` and `DEFERRED` redefined inside `createBatchCore`/`withholdNote` (kit:project/.agents/harness/files/batch.mjs:53-54 ; read_limits.mjs:99); `DEFERRED` and `MEDIA_HINT` are built from the kit defaults at import and ignore a project overlay (read_limits.mjs:24-25).
14. The 17-name list is duplicated in `TOOLS`, `register.ts:4` and `register.test.ts:3`; the media reply still mentions the "legacy filesystem MCP" (register.ts:80) and the binary hint mentions `read_media_file` (read_limits.mjs:25), both stale once adapters are dropped.
15. The mod returns `{result: text}` and ignores the backend `isError` (kit:project/.claude/plugins/harness-files/hooks/register.ts:92), so the model never receives an error flag; errors are recognisable only by text (`nothing written`, `ERROR (details/fix IDs ...)`). Whether the engine can flag results as errors is not shown in the sources.
16. Dead/legacy code to remove with the adapters: `_meta` on BATCH_TOOLS (batch.mjs:50), `mcp/*`, `read_media_file`, media counters, `INLINE_MAX_CHARS` (config.mjs:11), `machine.local.json` references (README:21).
17. The suggestion search runs binary searches with `includes` over the whole file for each failed edit (kit:project/.agents/harness/files/batch.mjs:184-186): costly on large files with many failures.
18. README admits macOS/Linux paths are not verified on real machines (kit:README.md:38); the 20 s lock test makes the suite slow (backend.test.mjs:224).

## Open questions for the owner

Q1. Architecture of the file tools in the new kit (affects FIL-01, 06, 07, 09, 13, 14, 17).
- Options: (A) keep the permission-gated mod with native-Bash tickets, but only 3 tools and a slimmer ticket protocol; (B) a long-lived stdio MCP server with in-memory state (fix IDs, tags), no tickets/locks/receipts, annotations for result size; (C) mod holding the state in memory and calling a stateless backend.
- Evidence: 0.1.0 replaced the MCP transport by the mod (CHANGELOG:34) without stating why beyond permission fidelity (README:109-111); legacy agents ran in bypass mode anyway (mcp_fs_proxy.mjs:8); a historical omp-era decision (2026-10-11, memory omp-migration-policy.md:18, which line 11 of the same file marks as "historical context, not the current direction") was "No MCP (MCP only for services outside the machine)"; it is not a current kit rule.
- Recommendation: (A) if permission-gated file tools matter for the main session, else (B). I cannot decide from the sources; please state why the MCP transport was replaced.

Q2. What should happen on `ask` (FIL-08)? Current behavior: the mod tools fail closed and the agent must use native tools, never a prompt.
- Options: keep; or return guidance to use native tools (same effect); or let Claude's own prompt handle it (needs native call, not possible for a custom tool).
- Recommendation: keep fail-closed, but confirm the permission mode of the `circle` main session and `circle-agent` workers so mod writes are not systematically refused.

Q3. Read limits for the mod path (FIL-23, 26).
- Options: (a) one page per call: set `replyMaxChars` near the 36,000 page size and `fileMaxChars` at or below it, so oversized reads give the "read lines a-b" hint; (b) keep 200,000/450,000 and accept up to ~13 continuation calls; (c) raise the page size toward 50,000 minus overhead.
- Recommendation: (a) with page size about 40,000 and an explicit continuation only for diagnostics.

Q4. Image-per-turn guard (FIL-43). The cap existed only in the dropped proxy; native Read has no such cap in the kit, and GPT-family models still run in Claude Code through `circle`.
- Options: drop the limit; add a kit-owned hook that counts native Read images per turn; leave it to Paseo/provider settings.
- Recommendation: keep it only if image-heavy GPT sessions are still used; otherwise drop and document the incident.

Q5. Keep tag/hash line edits (FIL-36..39, about 110 lines)? They were added in 0.1.0 to save output tokens (CHANGELOG:19); no usage data is in the sources.
- Options: keep all tiers; keep only in-place and moved-lines placement (drop suggestion/shown-lines tiers); drop line edits.
- Recommendation: keep, then measure on transcripts and trim the failure tiers if unused.
