# Code review: workflow

## Verdict

REVISE; 3 BLOCKER, 3 MAJOR, 0 MINOR. All 102 workflow tests passed (`node --test --test-reporter=dot 'tests/workflow/*.test.mjs'`), but they miss destructive run-directory reuse, concurrent calls sharing a session, admission races, interrupted-tool time accounting, and retries exceeding the advertised whole-call deadline. Read-only, in-memory probes reproduced the session leak, cap overrun, false watchdog stop, and deadline overrun; no real daemon, project, or owner configuration was used. The additional resume-metadata defect follows directly from the runner/journal/cache path. The documented integration extensions (`detail`, `timeoutS`, and `runId`) are treated as intentional, not findings merely because FLOW-04's option list has not caught up.

## Findings

### CR-WFL-01 BLOCKER correctness Run creation overwrites existing runs and accepts dot-directory IDs
- Severity: BLOCKER.
- Category: correctness.
- Where: `ship/.agents/harness/workflow/cmd-workflow.mjs:68`, `:83`, `:86-96`, `:128-136` (FLOW-18, FLOW-19, FLOW-20; INV-22).
- Evidence: The run-ID regex accepts both `.` and `..`. `path.join(runsDir, runId)` therefore need not designate a child run directory. `writeRunStart()` uses recursive mkdir and unconditional writes, without an exclusive claim or an existing-run refusal. Even an ordinary repeated `--run-id wf_x` overwrites the previous script, args and run metadata while appending to its old journal and log and retaining an old `result.json` if the new attempt fails. Two simultaneous invocations with the same ID corrupt each other's records. `--runs-dir . --run-id .` can overwrite project-root `script.js`, `args.json`, and `run.json`; `..` escapes the selected runs directory. A watcher can also see the previous terminal log line and declare a newly started run finished immediately. The FLOW-19 test rejects `../x`, but never checks dot-only IDs or collisions.
- Fix: Reject `.` and `..` and validate that the resolved run directory is a strict immediate child of the selected runs directory. Claim a new run directory exclusively before writing any artifact; reject an existing directory without modifying it, including when it is the resume source. Give the detached child a separate explicit, validated handoff for the directory reserved by its parent, rather than allowing arbitrary foreground invocations to reuse directories. Add collision, concurrent-claim, dot-ID, and same-source/destination resume tests asserting that existing bytes stay unchanged.

### CR-WFL-02 BLOCKER correctness Concurrent calls with one session key split the session and leak a worker
- Severity: BLOCKER.
- Category: correctness.
- Where: `ship/.agents/harness/workflow/runner.mjs:57-61`, `:112-115`, `:283-287`, `:300-305`; `ship/.agents/harness/workflow/engine.mjs:100-105` (FLOW-12, FLOW-47; INV-22).
- Evidence: Session compatibility is checked, but there is no per-key in-flight reservation or serialization. `sessions` is populated only after a successful call finishes. Consequently `parallel([() => agent('a', {session:'s'}), () => agent('b', {session:'s'})])` can admit both calls as new and create two independent agents. Both calls retain their worker; the last completion overwrites the map entry, and `finish()` archives only that entry. An in-memory probe through the actual engine and host produced `created:["fake-0","fake-1"], archived:["fake-1"], leaked:["fake-0"]`. With worktree isolation, the same logical session also splits into independent worktrees. Overlapping continuations of an already-established session can instead encounter the active-turn refusal and run the failure cleanup against the agent serving the other call. Existing session tests are all sequential.
- Fix: Serialize calls per session key, including adoption and cleanup, before deciding whether a new agent/worktree or live slot is required. Alternatively, reject overlapping calls for the same key as a named configuration error before either can mutate session state. Do not let failure cleanup from one call delete/archive a different in-flight call's session. Add parallel-first-call and parallel-continuation tests proving one agent/worktree and complete cleanup.

### CR-WFL-03 BLOCKER correctness First-hang recovery turns elapsed tool time into model time and can immediately stop the retry
- Severity: BLOCKER.
- Category: correctness.
- Where: `ship/.agents/harness/workflow/watchdog.mjs:122-142` (FLOW-29, FLOW-35, FLOW-37; INV-20).
- Evidence: On the first stuck call, `st.calls.clear()` discards every open tool span without recording its elapsed interval in `toolSpans`. `promptAt` remains unchanged, as required for watchdog messages. The next tick therefore counts the discarded tool duration as model time. Using shipped stop/tool limits, a probe with 950 seconds of model time followed by a 900-second Bash call measured 950 seconds of model time before the interrupt, then 1,860 seconds ten seconds afterward: events were `cancel`, retry `send`, `archive`, with reason `watchdog stopped the agent after 1800 s`. The retry gets stopped despite only 960 seconds of actual model time. A subsequent terminal event cannot recover the original interval because its call record was deleted. Current first-hang unit tests disable model-time stopping; the runner test uses a short hang and an immediate retry reply.
- Fix: Before clearing interrupted calls, close every complete-input open span at the interruption time and add it to the union-accounting history. Record the cleared call IDs as finished so late events cannot recreate them. Preserve the current prompt clock and stuck-interrupt flag. Add the model-time-plus-long-shell reproduction with stopping enabled and a non-instant retry, asserting no premature nudge/archive and correct model milliseconds.

### CR-WFL-04 MAJOR correctness Budget and agent-cap checks occur before an asynchronous admission wait
- Severity: MAJOR.
- Category: correctness.
- Where: `ship/.agents/harness/workflow/engine.mjs:143-159` (FLOW-09, FLOW-14, FLOW-43).
- Evidence: The second `checkBudget()`/`checkCap()` happens before `await host.admit(...)`, not after admission. Several calls can all pass the cap check against the same `state.started` and then each increment it. A pure-engine probe using `maxConcurrent:4`, `maxAgents:1`, and four parallel calls started all four (`started:4`, runner calls `[1,2,3,4]`). The existing cap test uses a larger cap than concurrency and staggered completions, so it does not expose the initial race. Likewise, a call waiting inside caller-wide admission can start after another call or the orchestrator has exhausted the budget: it never rechecks the updated spend. This is distinct from the permitted overshoot by agents already running.
- Fix: After successful host admission, recheck budget and cap immediately before allocating the start number/incrementing `state.started`, with no intervening await. Release the admission reservation in `finally` if either check throws, and write no start record for that call. Add `maxAgents < maxConcurrent` coverage and a deferred-admission fixture in which spend changes while admission is pending.

### CR-WFL-05 MAJOR correctness The whole-call timeout is only a per-wait argument and does not bound provider retries
- Severity: MAJOR.
- Category: correctness.
- Where: `ship/.agents/harness/workflow/runner.mjs:136-150`, `:159-168`; interaction with `ship/.agents/harness/paseo-client/index.mjs:112-141` (FLOW-04 integration extension; GSDF-50, GSDF-67; integration request for `timeoutS`).
- Evidence: `waitOpts()` calculates the remaining deadline once before `session.waitTurn()`. That method can sleep through provider-retry backoffs and repeat `waitForFinish()` with the original timeout multiple times. The host neither enforces an independent deadline nor checks it after a successful reply. An in-memory probe using the actual `Session.waitTurn`/`continueAfterError` methods, a five-second `timeoutS`, an immediate overload error and then success returned `status:"ok", result:"late success", durationS:30`. A longer transient-error sequence can exceed the fixer/debug deadline by much more. The integration test only uses one never-replying turn, with no provider retry, so it proves a single-wait timeout rather than the claimed whole-call deadline.
- Fix: Pass an absolute deadline/cancellation signal through the Session wait/retry path. Recompute remaining time before every wait and backoff, refuse to send a retry after expiry, and terminate/archive the timed-out call without leaving an outstanding continuation capable of sending later. Bound warm-up/creation phases consistently with the advertised whole-call deadline. Preserve the original `no reply within <timeoutS> s` reason. Add transient-error, permission-loop, and multi-turn/schema-retry deadline tests, including a reply arriving after the deadline.

### CR-WFL-06 MAJOR correctness Resume drops the worktree path from detailed non-session results
- Severity: MAJOR.
- Category: correctness.
- Where: `ship/.agents/harness/workflow/runner.mjs:135`; `ship/.agents/harness/workflow/engine.mjs:96`, `:111-115`, `:126-129` (FLOW-15, FLOW-27; FLOW-04 `detail` integration extension).
- Evidence: A live isolated call returns `worktreePath` for every worktree, but returns the serializable `worktree` object only when a session key exists. The engine's journal finish record saves only `r.worktree`, never `r.worktreePath`. Therefore a supported call such as `agent('implement', {isolation:'worktree', detail:true})` returns a usable worktree path initially, but a cache hit on resume returns the same successful result with `worktree:null`. The worker's changes still exist in the original worktree, while the resumed script loses the metadata needed to locate/integrate them. The detailed-result test checks only live calls, and the worktree-resume test always supplies a session key, bypassing this loss.
- Fix: Persist the worktree path/object for every isolated call, regardless of session use, and carry it unchanged through cached journal entries and the detailed-result wrapper. Keep session adoption conditional on a session key, not worktree metadata persistence. Add a non-session isolated detailed call followed by two resume generations and assert the returned worktree path remains the original one, no new worker/tree is created, and the original output remains accessible.
