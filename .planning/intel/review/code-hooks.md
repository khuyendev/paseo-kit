# Code review: hooks

## Verdict
REVISE — 0 BLOCKER, 3 MAJOR, 0 MINOR. The offline hook suite passes (53 tests, `node --test --test-reporter=dot "tests/hooks/*.test.mjs"`), but it misses recovery and concurrency failures in the context-band state and syntax-check semaphore, and a Windows path mismatch between the file tools and their syntax hook. These break explicit reminder, before/after-check, and machine-wide concurrency contracts. All source and test files in the assigned paths were read in full, together with the requirements, relevant synthesis/invariants/decisions, interfaces, integration reports, and hook behavior map. The findings below include read-only, in-memory probes; no real project, Claude configuration, or Paseo session was exercised. The documented live transcript/response-shape checks remain unverified, not counted as passing offline coverage.

## Findings

### CR-HOK-01 MAJOR correctness Context-band claims and resets are not one atomic state transition
- Severity: MAJOR.
- Category: correctness.
- Where: `ship/.claude/hooks/context_guard.mjs:57-94`; `tests/hooks/context_guard.test.mjs:64-101` (HOOK-09; INV-25; D-50).
- Evidence: `claimBand()` reads `state.json`, exclusively creates a claim, and separately replaces `state.json`; downward resets replace the state without coordinating with either operation. A crash after creating `claim-e0-b0` but before writing the first state leaves the authoritative band at its fallback `-1`. Subsequent below-threshold calls do not advance the epoch, and every later climb to band 0 encounters that same claim. An in-memory filesystem probe of this exact crash residue produced `reminds: false` for bands `[0, -1, 0, -1, 0]`. Thus a crash can lose more than one reminder, and compaction no longer re-arms it. There is also a lost-update race without a crash: starting at `{band:1,epoch:0}`, reset A reads that state and pauses; reset B writes `{band:0,epoch:1}`; a band-1 call claims epoch 1 and writes `{band:1,epoch:1}`; A then overwrites it with `{band:0,epoch:1}`. The next band-1 call is suppressed by the existing epoch-1 claim. The six-process test exercises only a fresh, identical upward band; the sequential reset tests cannot expose either case.
- Fix: Make the band, reset generation, and decision to remind one authoritative atomic transition, rather than a claim followed by a separate mutable state file. For example, publish fully written immutable successor records with an exclusive atomic link, retrying from the winning successor when another process wins; downward moves must use the same transition protocol. A committed reminder transition must remain visible even if the process dies before output, so a later downward transition can re-arm it. Do not introduce PID/mtime claim recovery. Add a crash-after-decision test and a controlled reset-versus-climb interleaving test, asserting that each later climb can remind exactly once.

### CR-HOK-02 MAJOR correctness Syntax targets do not resolve the Windows path forms accepted by the file tools
- Severity: MAJOR.
- Category: correctness.
- Where: `ship/.claude/hooks/syntax_check.mjs:22-33`, `:85-90`, `:184-190`; supporting contract implementation: `ship/.agents/harness/files/targets.mjs:11-24` (HOOK-26, HOOK-28; FTOL-19; INV-27, INV-52).
- Evidence: The syntax hook uses plain `path.resolve(cwd, p)`, while the two mod writers explicitly convert Git Bash drive paths and expand `~` before resolving them. On this Windows machine, a read-only call to `collectTargets({cwd:'C:/Work',tool_input:{files:[{path:'/c/Work/a.txt'}]}}, 'PreToolUse')` returned `C:\c\Work\a.txt`, not `C:\Work\a.txt`. The writer edits the latter. Pre therefore records an absent or unrelated file instead of checking the real target. Post can discover the real path from the writer's result, but it has no matching baseline and reports an existing syntax failure as a new error with `(not checked before this edit)`. This is an ordinary path-bearing edit, not the fix-only exception. If the misresolved path happens to exist, the hook can additionally run the checker on an unrelated file/tree. The same discrepancy affects `~/...` inputs. Existing hook tests use native or ordinary relative paths only.
- Fix: Normalize hook targets with the same path-form rules as the mod writers before deduplication, tree discovery, and Pre/Post keying: expand `~` consistently, translate `/c/...` on Windows, then resolve against the hook cwd. Put that pure normalization in a shared helper rather than importing the file backend's private state. Add Windows Pre/Post tests using a Git Bash path and its native spelling for the same target: a pre-existing failure must stay silent, a newly introduced failure must report without the missing-baseline marker, and only the intended target may be checked.

### CR-HOK-03 MAJOR invariant Stale-slot reclamation can delete a newly acquired slot and exceed the checker cap
- Severity: MAJOR.
- Category: invariant.
- Where: `ship/.claude/hooks/syntax_check.mjs:57-75`, `:98-109`; `tests/hooks/syntax_check.test.mjs:107-122` (HOOK-27; INV-27).
- Evidence: After `wx` fails, the hook separately stats a slot and unconditionally removes that pathname when the observed mtime is stale. Two hook processes can both observe an abandoned slot. A reads its old mtime and pauses; B removes it, acquires the same slot, and starts its checker; A resumes and deletes B's fresh lock based on the stale stat. A then acquires the slot too. With `max_parallel:1`, both checkers run concurrently; the unconditional release callback can also delete the replacement owner's lock. A read-only probe evaluated the shipped `acquireSlot()` with an in-memory filesystem simulating B's acquisition between A's stat and remove: `{max_parallel:1, acquiredA:true, stillRunningB:true, slotOwner:'A'}`. This is a realistic recovery path after a hook process dies and leaves a lock older than 180 seconds. The existing concurrency test starts from an empty slot directory and never exercises reclamation.
- Fix: Make allocation, stale reclamation, and release ownership-safe as one cross-process semaphore protocol. Serialize reclamation against allocation, revalidate expiry while holding that coordination, and use a unique acquisition token so an old release cannot remove a replacement slot. Do not rely on an uncoordinated stat-then-unlink or token-read-then-unlink sequence. Add a controlled two-process test with an abandoned slot that forces the stat/reacquire/remove interleaving and proves the running-check count never exceeds `max_parallel`; also assert that releasing an old acquisition cannot free the new owner's slot.
