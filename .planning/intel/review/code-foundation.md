# Code review: foundation (FND)

## Verdict

REVISE — 2 BLOCKER, 1 MAJOR, 0 MINOR. The config loader and most adapter contracts are implemented coherently, but Windows argv execution can interpret argument data as commands, creation cleanup can falsely report an agent archived and cause its worktree to be deleted, and provider retries defeat the workflow's whole-call deadline. Ran `node --test 'tests/foundation/*.test.mjs'`: 65 passed, 0 failed, 0 skipped. The findings below were checked with read-only, in-memory probes and a harmless Windows command-expansion probe; no real daemon, project installation, or owner configuration was exercised. The full suite and live/manual checks were not run.

## Findings

### CR-FND-01 BLOCKER security Windows argv quoting permits environment expansion and command injection

- Severity: BLOCKER.
- Category: security.
- Where: `ship/.agents/harness/lib/proc.mjs:22`, `ship/.agents/harness/lib/proc.mjs:36-40`; also consumed by `ship/.agents/harness/platform.mjs:45-46` (INV-52; shared argv execution contract in `docs/INTERFACES.md:217`).
- Evidence: `cmdWord` treats `%` as a plain, safe character, and the `.cmd`/`.bat` path concatenates these words into a command run with `shell: true`. Arguments are therefore not literal argv: cmd.exe expands `%NAME%`, and unquoted expansion can introduce command separators. A read-only probe using exactly this renderer and shell invocation, with argument `%FND_PROBE%` and environment value `FND_PROBE=original & echo INJECTED`, produced two output lines, `original` and `INJECTED`, instead of the literal argument. This affects adapter commands run through npm-style shims and the shared Claude CLI wrapper; it also corrupts legitimate percent-containing arguments. `tests/foundation/platform-lib.test.mjs:136-151` proves literal metacharacters only for a direct `.exe`; its `.cmd` case passes only `there`, so it does not cover this branch's argument safety.
- Fix: Make the Windows shim branch preserve literal arguments rather than relying on `cmdWord` plus `shell: true`. Prefer invoking the underlying Node entry point directly for Node/npm CLIs. For remaining batch executables, use a thoroughly tested cmd-specific transport, or reject argument characters that cannot be transported literally (including environment-expansion and line-break forms) before execution. Apply the same policy to `runClaude`. Add Windows argument round-trip tests for `%NAME%`, `!NAME!`, quotes, trailing backslashes, spaces and shell metacharacters, and a harmless marker-command assertion proving argument expansion cannot execute a second command.

### CR-FND-02 BLOCKER correctness Failed archive is hidden as successful cleanup after agent creation

- Severity: BLOCKER.
- Category: correctness.
- Where: `ship/.agents/harness/paseo-client/index.mjs:85-90`; downstream cleanup at `ship/.agents/harness/runtime/start.mjs:77-79`, `ship/.agents/harness/runtime/worktrees.mjs:51-54`, and `ship/.agents/harness/workflow/runner.mjs:271-280` (PCLI-11; INV-04, INV-12, INV-15).
- Evidence: Once `createAgent` has started a worker, a usage-subscription failure triggers `archiveAgent(...).catch(() => {})`. Even if archiving fails, the thrown error says `(archived)` and exposes no structured agent identity or cleanup outcome. An in-memory client whose subscription rejects with `subscription lost` and whose archive rejects with `transport closed before archive` produced `agent 12345678 created but its usage tracking failed (archived): subscription lost` while the worker remained live. This is a particularly plausible pair of failures on transport loss. Both creation callers treat the rejection as though no agent exists: `startAgent` immediately force-removes the new worktree and deletes its branch, and the workflow runner also removes a new worktree when its local `agentId` was never assigned. The live worker can thus lose its working directory or already-written changes; its capacity reservation is also no longer reliable. The existing PCLI-11 failure test asserts only that an archive call occurred, not that it succeeded.
- Fix: Preserve the full created-agent ID and the distinction between confirmed archive and failed/unknown cleanup in a structured creation error. Say `(archived)` only after archive confirmation; otherwise report the archive error and the live/unknown agent ID. Update both callers to retain the worktree and account for the created agent whenever creation succeeded but cleanup is unconfirmed. Do not force-remove a worktree merely because post-creation tracking failed. Add a regression with both subscription and archive failures, asserting accurate reporting, preserved worktree, and retained agent identity/capacity bookkeeping.

### CR-FND-03 MAJOR correctness Retry loops reset the wait allowance and bypass whole-call deadlines

- Severity: MAJOR.
- Category: correctness.
- Where: `ship/.agents/harness/paseo-client/index.mjs:112-125`, `ship/.agents/harness/paseo-client/index.mjs:129-150`; caller at `ship/.agents/harness/workflow/runner.mjs:136-150` and `:247-249` (PCLI-12/PCLI-13; GSDF-50/GSDF-67 deadline consumers; integration report's `timeoutS` whole-call contract).
- Evidence: Every iteration passes the original `timeoutS * 1000` to `waitForFinish`, and `continueAfterError` sleeps the full 30/60/120/240/300 seconds without consulting a deadline. The workflow runner calculates the remaining whole-call allowance only once when entering `session.waitTurn`; it has no timer that interrupts this internal retry loop and does not reject a successful reply received after the deadline. A fake-clock probe with `timeoutS: 1`, an overload error after 999 ms, and a successful retry after another 999 ms returned `done` after **31,998 ms**, including a continuation sent after the one-second allowance had expired. With multiple transient failures this exceeds the intended limit by minutes; permission loops similarly receive fresh full waits. The PCLI-13 tests verify retry pauses, but never combine retries with a deadline.
- Fix: Carry an absolute deadline through `waitTurn` and its retry/permission paths, preferably explicitly from the workflow runner for whole-call limits. Before sleeping, sending a continuation, or starting another wait, check the remaining time; cap sleeps and waits to that remainder and fail with the timeout reason when it is exhausted. Ensure the runner checks the deadline before accepting a successful result and performs its normal timeout cleanup. Preserve the five-retry policy when sufficient time remains. Add fake-clock tests for an overload near the deadline, a deadline during backoff, and repeated permission responses; assert no continuation is sent after expiry and the workflow cannot return success beyond its whole-call limit.
