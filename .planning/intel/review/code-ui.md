# Code review: PNL — Paseo planning panel and swarm map

## Verdict

REVISE — 2 BLOCKER, 9 MAJOR, 0 MINOR. The offline UI suite passes all 77 tests, including both TypeScript checks, but neither server bundle can load through the installed Paseo 0.11.2 compiler/evaluator. Beyond that release blocker, the observer executes project-controlled modules, planning aggregation can show obsolete or invalid work as complete, and several required UI behaviors are not exercised by the helper/source-text tests. Review validation used the offline suite, the installed compiler with `write: false` and no daemon connection, and read-only/in-memory reproductions; no live configuration, projects, agents, or upstream code were run or changed.

## Findings

### CR-PNL-01 BLOCKER correctness Both plugins fail during real host bundle evaluation
- Severity: BLOCKER.
- Category: correctness.
- Where: `plugins/planning-panel/server/gsd-link.ts:10`; `plugins/swarm-map/server/rotate.ts:18`; `tests/ui/plugin-gates.test.mjs:39` (PANL-01, PANL-02, PANL-10).
- Evidence: Both modules evaluate `fileURLToPath(import.meta.url)` at module initialization. The installed Paseo 0.11.2 compiler bundles servers as CommonJS (`@getpaseo/server/dist/server/server/plugins/compiler.js:317-320`), and its evaluator evaluates the bundle rather than importing the original source file (`bundle-evaluator.js:30-35`). Esbuild replaces `import.meta` with an empty object in that output. Compiling each server entry with the installed `compilePlugin` and passing its in-memory output to `evaluateBundle` reproduced the same failure for both: `ERR_INVALID_ARG_TYPE The "path" argument must be of type string or an instance of URL. Received undefined`. This occurs before `contribute` can register any RPC. Direct Node imports and `tsc --noEmit` do not test the deployed loading path.
- Fix: Remove source-location-dependent initialization from the plugin runtime. Package/bundle the trusted shared readers and defaults in a form supported by Paseo's CommonJS compiler, with explicit inputs for project data paths instead of discovering the kit via `import.meta.url`. Add an offline gate using the pinned host compiler and evaluator for both entry points, then assert registration on the fake host. Extend the smoke beyond checking SDK methods: it must establish that these plugin bundles actually load.

### CR-PNL-02 BLOCKER security Read-only observers execute arbitrary modules from observed projects
- Severity: BLOCKER.
- Category: security.
- Where: `plugins/planning-panel/server/gsd-link.ts:24-30,40-43`; `plugins/swarm-map/server/rotate.ts:20-21,49-53`; `plugins/swarm-map/server/snapshot.ts:80-93`; `tests/ui/plugin-gates.test.mjs:49-64` (PANL-05, PANL-55, INV-56).
- Evidence: The planning panel dynamically imports the workspace's `status.mjs` and `planning.mjs` merely because their paths exist; the swarm map dynamically imports a discovered project's `config.mjs`. Neither path verifies provenance or requires authorization to execute that project's code. Import executes top-level code and its transitive imports with the plugin process's filesystem/environment access. In particular, the swarm does this for every listed agent's cwd before applying the drawn/recent filters, so even a standalone agent can cause project code execution. A project-controlled replacement module with a top-level side effect runs simply when the observer polls. This is distinct from deliberately running that project's installed `ph`. The read-only grep gate scans only plugin source, so it does not establish the claimed guarantee across these dynamic imports. This remains a security issue after CR-PNL-01 is fixed.
- Fix: Execute only trusted kit-shipped/bundled reader and validation code. Read project defaults, overlays and planning artifacts as data through those helpers; parameterize the trusted config loader with the project's defaults file so PANL-55 still uses installed defaults. Do not select executable modules by workspace path. Add an offline test with a project module containing an observable in-memory sentinel and assert that polling never imports it.

### CR-PNL-03 MAJOR invariant Phase-status cache never notices changed verification-covered source files
- Severity: MAJOR.
- Category: invariant.
- Where: `plugins/planning-panel/server/board.ts:23-27`; `plugins/planning-panel/server/gsd-link.ts:47-56`; `plugins/planning-panel/server/service.ts:49` (PANL-15, PANL-07, INV-36, INV-43).
- Evidence: A phase's cache signature contains only paths and mtimes underneath its `.planning/phases/<phase>/` directory. The actual GSD ladder checks the verification fingerprint of `covered_files`, including source files outside `.planning/` (`ship/.agents/harness/gsd/status.mjs:81-89,119-126`). After the panel caches `COMPLETE`, editing a covered source file changes the CLI answer to `NEEDS_REVIEW` but leaves the panel signature unchanged. The cache has no expiration; even the Refresh button continues returning the cached completion. An in-memory reproduction changing the backing status from `COMPLETE` to `NEEDS_REVIEW` with an unchanged phase signature returned `COMPLETE` again.
- Fix: Invalidate against every input of the ladder, including verification-covered files outside the phase directory, or recompute the authoritative ladder on each poll while caching only safe file reads. Never retain `COMPLETE` solely on phase-directory mtimes. Add a test that creates a valid completed fixture, polls, changes a covered source file only, and compares the second board result with `roadmap analyze`.

### CR-PNL-04 MAJOR spec Roadmap-only and empty phases disappear from the board and totals
- Severity: MAJOR.
- Category: spec.
- Where: `plugins/planning-panel/server/board.ts:7-12`; `plugins/planning-panel/server/service.ts:38`; `tests/ui/planning-frontmatter.test.mjs:70-91` (PANL-15, PANL-19).
- Evidence: `phasesOf` discovers phases only from indexed files with a `phases/<id>/...` path. It never reads the phase entries in ROADMAP.md and cannot see an empty directory. In contrast, GSD `analyze` enumerates roadmap phases and reports missing directories as `NOT_STARTED` (`ship/.agents/harness/gsd/phases.mjs:22-29`); `phase add` and `phase insert` create empty directories. Thus a newly planned project or newly added phase is absent from the UI until some artifact is written, and phase progress can become 100% by omitting all future phases. The parity test creates a CONTEXT file for its supposedly empty phase and omits roadmap-only phases, so it cannot catch this divergence. The pure reproduction `phasesOf([ROADMAP entry])` returns `[]`.
- Fix: Build the phase roster from the same roadmap semantics as `roadmap analyze`, representing unresolved directories explicitly, and reconcile discovered directories without requiring a file inside each. Update board/index schemas and navigation as needed for a phase without an artifact. Test roadmap-only, empty-directory and completed-plus-future-phase cases against the CLI, not just populated phase fixtures.

### CR-PNL-05 MAJOR correctness Superseded plans and summaries are reused as live planning state
- Severity: MAJOR.
- Category: correctness.
- Where: `plugins/planning-panel/server/kinds.ts:26-33`; `plugins/planning-panel/server/board.ts:33-40`; `plugins/planning-panel/server/service.ts:75-84`; `plugins/planning-panel/client/stats.ts:25-29` (PANL-15, PANL-16, PANL-19).
- Evidence: Classification uses the basename regardless of nesting, and board/stat/detail consumers select all matching artifacts below the phase. GSD `supersede` moves retired PLAN and SUMMARY files to `superseded/` with those same basenames (`ship/.agents/harness/gsd/artifacts.mjs:233-246`), while GSD's live inventory reads only direct children. The UI counts the retired plans, and its summary lookup can attach a retired summary to a replacement active plan with the same id. For example, an active `01-01-PLAN.md` with no current summary plus `superseded/01-01-SUMMARY.md` is shown done. A phase containing only a retired plan/summary pair also produces `plans:1, done:1, pct:100` in the board reproduction.
- Fix: Keep historical artifacts browsable in Files, but explicitly distinguish them from the active phase inventory. Board, stats and plan lookup must use direct active phase children; resolve a plan's summary as its exact sibling path, not any matching phase/id in the recursive index. Test retired-only files and a replacement plan whose only matching SUMMARY is under `superseded/`.

### CR-PNL-06 MAJOR invariant Unparseable summaries turn into successful completion
- Severity: MAJOR.
- Category: invariant.
- Where: `plugins/planning-panel/server/indexer.ts:54-58`; `plugins/planning-panel/server/board.ts:35-40`; `plugins/planning-panel/client/stats.ts:26-29`; `plugins/planning-panel/client/views.tsx:115-121`; `plugins/swarm-map/server/wave-link.ts:24-32,89-96` (PANL-14, PANL-15, PANL-19, PANL-61, INV-36).
- Evidence: An index entry with invalid SUMMARY frontmatter retains `status:null` plus `error`. Completion consumers ignore `error`, and `summaryDone(null)` means done. An in-memory board fixture with one valid PLAN and one malformed SUMMARY yielded `done:1, pct:100`; the Phases view also renders its successful check icon. The swarm wave reader has an independent permissive regex parser: an unfinished or malformed block with no readable status becomes null and is likewise counted done with `scope:"complete"`. It additionally collapses unreadable and absent summaries into the same null return. This converts inability to parse/read evidence into authoritative completion or authoritative counts.
- Fix: Keep missing optional status distinct from failed parsing/reading. Only a successfully parsed existing summary may use the absent-status completion convention. Surface the affected file's diagnostic, withhold completion/percentages where evidence is unknown, and have the wave reader use the conformant parser and distinguish ENOENT from other failures. Add malformed, unfinished and unreadable SUMMARY cases to board, stats and wave tests.

### CR-PNL-07 MAJOR correctness File ledger merges different projects and splits aliases of the same file
- Severity: MAJOR.
- Category: correctness.
- Where: `plugins/swarm-map/server/activity.ts:166-170`; `plugins/swarm-map/server/files.ts:28-30,40-45`; `plugins/swarm-map/server/snapshot.ts:186` (PANL-34, PANL-37, PANL-38, PANL-60).
- Evidence: Activity paths enter a daemon-wide ledger verbatim, and its key only lowercases and replaces slashes. The activity target does not carry cwd. Relative paths are valid for the kit's file tools, so `src/index.ts` in two unrelated projects becomes one file, while `src/index.ts` and `C:/project/src/index.ts` in the same project become two files. A fake-SDK reproduction with agent A at `C:/project-a` and B at `C:/project-b`, each writing relative `src/index.ts`, produced one hold owned by B with `prevAgentId:"a", writers:2`. The map consequently reports a false write conflict and can miss a genuine mixed-relative/absolute conflict.
- Fix: Carry each agent's effective working directory into ledger ingestion and resolve file paths against it before normalization/keying, using the runtime's Windows/Git-Bash path rules. Preserve a display path separately if desired. Do not merge unresolved relative paths across agents/projects. Test different projects with identical relative paths, and relative/absolute spellings of one file within a project.

### CR-PNL-08 MAJOR spec Planning detail panes hide transport failures and never refresh open content
- Severity: MAJOR.
- Category: spec.
- Where: `plugins/planning-panel/client/data.ts:20-27`; `plugins/planning-panel/client/details.tsx:43-47,93-97`; `plugins/planning-panel/client/panel.tsx:68` (PANL-04, PANL-07, PANL-16, PANL-17, PANL-21).
- Evidence: Both detail components handle `ok:false` responses but never inspect `q.error`/`q.isError`. If a detail request rejects with no data, the loading branch remains forever after retries are exhausted. With cached data, a transport failure is invisible. Neither detail query has a polling interval or invalidation tied to the polled index; the panel's Refresh button refetches only index and board. An open plan therefore continues to show its old summary state after execution finishes, and an open file continues to show old text even after the user presses Refresh. The tests exercise `responseMatches` only, not request failures or updates of a mounted pane.
- Fix: Add transport-error/reconnecting states to both panes, with a retry action and a clear stale-data indication. Poll details while mounted or invalidate them when their relevant indexed mtimes change (including SUMMARY addition/removal for plans), and make the panel refresh include the active detail. Test initial rejection, refetch rejection, reconnection, edited file content and a newly added summary while the same detail stays open.

### CR-PNL-09 MAJOR spec Every phase-card navigation target is a directory passed to the file reader
- Severity: MAJOR.
- Category: spec.
- Where: `plugins/planning-panel/client/views.tsx:80-81`; `plugins/planning-panel/client/panel.tsx:85-86`; `plugins/planning-panel/server/service.ts:90-101` (PANL-15, PANL-17, PANL-21).
- Evidence: The board's only phase-card action is labelled `Open phase ... folder`, but dispatches `{kind:"file", path:phase.dir}`. The panel mounts `FileReader`, whose RPC opens that directory with `readDocument` as though it were a regular file. On Windows this returns an unreadable error instead of revealing a folder or that phase's plans. There is no folder navigation case in the trail or file reader. This affects every populated phase card and is not covered by the reducer-only navigation test.
- Fix: Add an explicit phase/folder navigation action that switches to the phase's plan list or to Files with that folder expanded and revealed; never send a directory to `planning.file`. Alternatively, link to a specific existing phase document and label the action accordingly. Add a rendered interaction test clicking a board card and asserting the intended list/reader rather than an unreadable envelope.

### CR-PNL-10 MAJOR spec Appearance bookkeeping disables the required boot and spawn animations
- Severity: MAJOR.
- Category: spec.
- Where: `plugins/swarm-map/client/swarm-surface.tsx:173,186-188,197-234`; `plugins/swarm-map/client/anim.ts:38-49`; `tests/ui/swarm-client.test.mjs:204-210` (PANL-49).
- Evidence: Canvas layout is derived from the separate `data` state. When a response arrives, the effect adds all incoming ids to `known`, sets `booted.current = true`, and updates `shownViewKey` before calling `setData(res)`. The next render is the first render containing the new nodes, but `appear(id)` already returns `none` because those ids are known. `useAppear` is mount-only, so it cannot recover later. Initial nodes do not boot-fade and subsequent new agents do not spring in; the same ordering defeats the filter-change boot mode. The PANL-49 test merely matches the expression in the source and checks timing constants, so it passes while the actual behavior is absent.
- Fix: Compute and store per-response appearance modes before mutating the previous-render bookkeeping, then supply those modes when new nodes first render. Commit the previous/known state only after rendering those nodes, or carry immutable appearance metadata alongside the new snapshot. Replace the regex-only acceptance with a mounted first-response/spawn/filter-change test that asserts the modes seen by newly mounted nodes.

### CR-PNL-11 MAJOR security Wave linking follows junctions outside the project
- Severity: MAJOR.
- Category: security.
- Where: `plugins/swarm-map/server/wave-link.ts:63-80,89-94` (PANL-61, PANL-13, INV-56, INV-52).
- Evidence: Wave linking checks only lexical `resolve`/`relative` containment. It then follows filesystem links through `fs.stat`, `fs.readFile` and `fs.readdir`. A run with `phaseDir:".planning/phases/02-link"` passes the check even when `02-link` is a Windows junction to an unrelated directory; matching plan and summary files there are read and exposed as the current project's wave progress. Links on `_workspace/_runs/<runId>` or individual artifact files are also followed. Unlike `planning.file`, this new read path has no realpath containment check, despite requiring the linked phase to be inside that project's `.planning/phases/`.
- Fix: Canonicalize and validate the run directory, phase directory and each file against their intended project roots before reading, and reject escaping symlinks/junctions (or refuse links entirely). Use the same containment discipline as the planning reader rather than a second lexical-only implementation. Add offline Windows-junction fixtures for a linked phase, a linked run directory and a linked artifact; each must remain unlinked or return an explicit unavailable scope without reading external artifacts.
