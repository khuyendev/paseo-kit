# gsd-execute

## Kit contract

Method text: the orchestration of upstream `execute-phase` is the workflow script below; for each plan follow `.agents/gsd/generated/workflows/execute-plan.md` (generated upstream text, unchanged; the executor's deviation rules, `.agents/gsd/generated/executor-rules.md`, reach it through its role include), then apply `.agents/workflows/gsd-overlay.md` and the project section below (overlays win).

The workflow is the project's composition `.agents/workflows/gsd-execute.js`: a script of kit verbs that the project owns and evolves. This block is the kit's contract for every composition; the project section below the markers describes what this project's script takes and returns.

Run: write the args file `_workspace/args/gsd-execute.json` (its fields are in the project section), run `node .agents/harness/ph.mjs workflow --name gsd-execute --args-file _workspace/args/gsd-execute.json --detach` and wait as its `next:` line says. A run that died is continued with `node .agents/harness/ph.mjs workflow --resume <runId>` (finished agent calls replay from the journal); a stopped run is answered, then run again with the same args.

Result statuses (the success statuses, stages and fields of this script are in the project section):
- `needs-owner`: show `stage`, `reason` and the numbered `options`, with the items the result lists for that stage. The answer is the verb the result names (an option, or the answer line of the stop, such as a `ph gsd ... clear` verb): run it as written, then run again with the same args. A stop that names no verb is answered by fixing the tree or the inputs it names, then running again. Quota or rate limits never offer retry-now: report the reset time.
- `refused`: another run holds the lease or lock the reason names; nothing was dispatched. Wait for it to end, then run again.
- `failed`: report the reason and the problems the result lists.
- Never edit the flow's state or record files by hand (progress, transfer, halt, request, answer and revision records, run journals under `_workspace/_runs/`): only the run and the `ph gsd` / `gsd-flow.mjs` verbs write them. Never edit the workflow script to get past a stop: composition changes go through harness-evolve between runs.

## Project composition

This section is the project's (outside the kit markers; kit updates never change it). It describes `.agents/workflows/gsd-execute.js` as this project runs it: args, switches, stages and result fields. harness-evolve changes it together with the script; seeded from the kit default.

### Run (GSDF-93)
Args file `_workspace/args/gsd-execute.json`: `{"phaseDir": ...}` plus `wave` (N), `plans` (`"03-01,03-02"`), `gapsOnly` (true) or `files` (an explicit review file list for the per-plan reviews; the batch phase review always covers the whole phase diff). Run `node .agents/harness/ph.mjs workflow --name gsd-execute --args-file _workspace/args/gsd-execute.json --detach` and wait as `next:` says. Never start execution from inside a `ph` agent worktree or on a `harness/*` branch (the run refuses and lists stranded commits and dirty files).

### Pause at a wave boundary (kit feedback 88)
- `stopAfterWave` (N, integer >= 1) in the args ends the run `paused` once wave N is committed and tracked, before a later wave starts. `node .agents/harness/ph.mjs workflow stop <runId>` (default `--at wave-boundary`, optional `--reason`) asks a running run to do the same at its next boundary; it kills nothing.
- Waves schedule: the run checks before each wave that has work left, so a stop never lands mid-wave: the running wave finishes its executors, gate, review and commit first. Graph schedule (`gsd.execute_schedule: graph`): no new plan starts (a plan of a wave past `stopAfterWave`, or any plan once a stop request is seen); the plans already started run on to their commit, then the run pauses (`notStarted` lists the plans held back). Batch mode commits once after the last wave: it refuses `stopAfterWave` and logs a stop request it cannot honour.
- Result `paused` (stage `Wave`): `reason`, `pausedAt {by: stopAfterWave | stop-request, afterWave, nextWave}` (`afterWave` is null before the first wave) and `answer` (verb `rerun`). After a stop request, rerun with the same args (or `ph workflow --resume <runId>`); after `stopAfterWave`, rerun without it or with a higher one (the same args pause again at once). The rerun goes on with the next wave; the committed waves stay tracked. The run's `run.json` status is `paused`; `ph runs` shows it, and a running run with a pending request as `stop requested`.

### What the run does
- Refuses a phase without `handoff/` (plan it first), a `--wave` while lower waves are incomplete, and `--gaps-only` when a plan lacks the `gap_closure` key.
- Refuses a handoff that no longer matches the plans (a plan edited, added or deleted after the handoff, or a wave set cut short by a failed handoff): plan the phase again.
- Owns grammar (kit feedback 74): an owns entry is a path, a directory or a glob; the transfer, the changed-file matching, request routing and the gate use the same matcher as the plan checker. A glob entry is less specific than a path or the files of a deeper entry; a worktree file matching no owns entry is still refused.
- Safe resume: an execute baseline is recorded once; before every dispatch changed files are matched to plans (a nested path belongs to the plan owning it most specifically; a tie between equally specific owners goes to the plan whose transfer record holds the path, the latest one when several do), and an incomplete plan with changes, an unowned changed path, a foreign HEAD move or commits without a SUMMARY stop the run (`needs-owner` with paths, owning plan and HEAD; options close out manually, re-execute from scratch, mark and skip). A commit between runs that touches no file any plan of the phase owns (a docs commit) is accepted and logged; a commit of the run whose `commits.json` record failed is reconciled from its `Plans:` trailer. Paths matching `adapter.ownership.ignore` (notes the owner keeps during a run) are never plan output. When the adapter sets `adapter.ownership.source_roots`, a changed path no plan owns that lies outside every source root (an orchestrator's note in `docs/`) is listed in the result's `outsideRoots`, left out of the wave commit and not a stop (`gsd.unowned_outside_roots`, default `report`; `stop` stops on every unowned path); a path inside a source root still stops with `paths`, and the first option is to commit those paths on their own (the commit touches no plan-owned file, so the resume gate accepts it). A tracked file no plan owns whose only change is line endings is listed in `eolOnly`, never committed and never a stop (the worktree transfer drops it the same way); a real content change of it still stops. Edit the main tree between runs, or commit at once. All resume state is in `execute-progress.json` (shared changes, requests, integration files, smoke build, commits, tracked plans), so a run that stopped or died at any step is followed by a run with the same args and no hand action. After an owner's hand fix to a file a plan transferred, record it with `node .agents/workflows/lib/gsd-flow.mjs adopt <phaseDir> <plan> <path>`: it re-hashes that path in the plan's transfer record and refuses a path that record does not hold or a transfer that did not finish. Never edit a transfer record by hand.
- Halts: a halted plan (Rule 4, checkpoint, failed executor) and its dependants are skipped and listed in the result's `skipped`; answer the halt with `node .agents/harness/ph.mjs gsd halt clear <N> --plan <id> --reason "<answer>"` and rerun: the plan is dispatched again with the answer in its prompt. When the halt was an owner decision about a finished executor result (its SUMMARY is in the worktree) and the work stands, add `--resume` (kit feedback 79): the next run transfers that worktree, runs no executor, and goes on to the gate; `halt clear --resume` refuses a halt without a finished worktree.
- Pending requests and kit notes (kit feedback 79): an executor reports a task that is done on its side but passes only once a request it routed is made as status `pending-request` with `blockedBy [request paths]`; it is no owner decision when every path is a request that plan routed (shared step before the gate, then the plan's obligations and the suite prove it; commit stays blocked while a request is open). A `partial` task is excused the same way when its evidence names only routed request paths. `gsd.pending_request_tasks: false` brings back the earlier rule (every partial task halts). The result lists `pendingRequestTasks [{plan, task, blockedBy, via}]`. Executors put observations about the kit in `kitNotes`; the run logs them and returns `kitNotes [{plan, note}]` (show them to the owner). A request for a `kit-feedback.md` file is refused and recorded as a kit note, never routed to a fixer.
- Change requests: a request for a file another open plan owns reaches that plan's executor or fixer; a request for a file no open plan owns (none, or a plan already committed) and the plans' `<shared_changes>` of the wave are made by one integration fixer owning exactly those paths before the gate, and committed with the wave. A review fixer that needs a file a committed plan owns and cannot change it stops the run `needs-owner` with `grantRequests` (each path and its owning plan) and one option per path: `node .agents/harness/ph.mjs gsd grant <N> --path <file> --plan <id>` (no `--plan` when no plan owns the file), then rerun with the same args. The grant lets the phase's fixers change that file, and the file joins the wave commit as integration, recorded in `commits.json`.
- Shared changes and requests, and how a stop is answered (kit feedback 82, 85, 83): the integration fixer of the shared changes reports per change (`changes`); a change counts as applied when the fixer says it is present, whatever it thinks of the rest of the tree, because the gate that follows verifies (its brief limits its checks to the shared files and sends other failures to the gate). An Integration stop is answered with `node .agents/harness/ph.mjs gsd shared clear <N> <wave> [--path <file>] --reason "<what you did or accept>"`. Before a Commit each open cross-plan request is checked (`gsd.request_check`): closed when its path changed since the request, when a shared change covers it, or when one read-only resolver call finds it present (the result lists them in `requestsClosed` with the basis); what is left stops the Commit with `node .agents/harness/ph.mjs gsd request clear <N> --plan <id> --path <file> --reason "<why it is satisfied>"` as the answer. The verbs record the answer in `owner-answers.json` (never edit `execute-progress.json`); rerun with the same args and the run takes it first and lists it in `ownerAnswers`.
- Execute state (kit feedback 83, 86, 87): `execute-progress.json` is written only by the `state-*` flow verbs (`node .agents/workflows/lib/gsd-flow.mjs state-read <phaseDir>` shows it; never edit it by hand, a raw `gsd-flow.mjs write` of it is refused). Every needs-owner result names its answer in `answer: {verb, command}`; run that command, then rerun with the same args. A request for a generated file (`adapter.ownership.regenerated`) names its generator (`via`) and every file it rewrites (`outputs`); without them it is held and the run stops at Integration: run the generator, then `ph gsd shared clear <N> <wave> --path <file> --reason "<generator and outputs>"`.
- One `gsd-executor` (or the adapter's executor agent) per plan, at most `gsd.parallelization.max_concurrent` at a time (one at a time when parallelization is off); plans sharing a modified file run one after the other. With `gsd.isolation: worktree` each executor works in its own worktree and the orchestrator transfers the owned changes in plan order. A change outside a plan's owns refuses its transfer (the plan halts), except a path matching `adapter.ownership.regenerated` or a tracked file that differs from HEAD only in line endings: those are dropped, logged as `transfer <plan>: <path> not copied`, and listed in the transfer record. The executor brief tells executors to delete the scratch files they create outside owns before they return. Worktrees do not pile up (kit-feedback 75): the transfer record keeps `wt_sha256` (the worktree content copied) per path; once a plan's commit is recorded the script discards its worktree and branch (`gsd-flow discard-worktree`), but only when every changed path of the tree is in the record with the same hash (anything else stays and is listed in the result's `worktrees.kept` with the reason). A halted plan's worktree stays and its name moves into `halt-answers.json` with `ph gsd halt clear`; when a later run dispatches the plan again it discards that tree (not a resumed run of the same id, and not while its run still uses it). Every removal first unlinks all symlinks and junctions inside the tree and refuses when one stays. The result lists `worktrees: {discarded, kept}` and `leftoverWorktrees` (harness worktrees of finished runs still on disk; `ph worktrees --prune` removes the `transferred` ones; `ph doctor` notes them too).
- Checks (kit feedback 87 C1): every gate also compares the test and gate files changed since HEAD (deleted test files, removed tests, fewer assertions, added skips, a changed gate file) and the gate configuration (`adapter.commands`, `verify_vocabulary`, `checks`) with the phase baseline. A weakening that no plan declares in `<check_changes>` stops the run `needs-owner` at stage Checks; no fixer is sent to it. Restore the check and rerun, or, when the change is right, answer with `node .agents/harness/ph.mjs gsd allow <N> --path <file> --reason "<why>"` (for the configuration `--path .agents/harness.config.json`; the allow holds for that path for the whole phase, for the configuration only as it is now) and rerun.
- Smoke build (F57): the first wave (`per-wave`) or the batch (`batch`) that changes a file matching `adapter.smoke_triggers` (dependency manifests, native-asset package files) builds `adapter.commands.smoke_builds` once per phase, before its gate. A failing or unrunnable target stops the run `needs-owner` at stage Smoke build with the failing argv and output; a passed build is kept in `execute-progress.json`, so a resumed run does not build again. Nothing runs while `smoke_builds` is empty.
- Gate after each wave (`per-wave`) or once at the end (`batch`): adapter gates, build, tests, every plan obligation; one evidence file per gate run under `<phaseDir>/evidence/`. In `per-wave` one more gate runs after the last wave is committed, over every plan of the run (`batch-<n>.json`, kit-feedback 58): a wave's gate goes stale once a later wave edits the same files, so that file is the phase's evidence. A red phase gate stops the run with the waves still tracked. Tracking (STATE wave log) moves only on green evidence.
- Review after green: one `gsd-code-reviewer` per plan, blocking findings verified by `finding-verifier` (a second, independent verifier decides what the first left uncertain), one `gsd-code-fixer` pass, a resolution check, and one more fixer pass limited to the findings still unresolved; one finding per defect class carries its instances. A rerun reuses the recorded review of unchanged code, and after a fix pass (a stop at Review, or a hand fix of the last instances) runs only the resolution check. Main-tree edits outside every plan's owns stop the run before the gate and the review. Non-blocking findings, and findings outside the lines the plan changed that the change did not cause (pre-existing), go to `<phaseDir>/deferred.md`; metrics to `_workspace/review-metrics.jsonl`. With `gsd.review_metrics` (default on) the verifier also tags each confirmed finding plan-catchable, and every executor halt, red gate and fix call (per wave, or per plan and commit batch under the graph schedule) is recorded with the plan defects named for it in `<phaseDir>/prereview/execute-<runId>.json` (measurement only; `ph review-stats --stage`). With `gsd.review_metrics` the run first scans for hand edits (plans, artifacts, transferred owned files changed outside the flow since their last record): `handEdits {pending, candidates, ask}` in the result and the log; show them, ask the owner for the cause and log it with `ph gsd hand-edit record <phase> <HE-n> --category contract-drift|wrong-api|owns-reach|test-fixture|other --note "<one line>"`. The run does not stop for them.
- Commits by the orchestrator only (`feat(<phase>-w<k>)` per wave or `feat(<phase>-<plan>)` per plan with a `Plans:` trailer), recorded in `<phaseDir>/commits.json`.
- Schedule (`gsd.execute_schedule`, kit-feedback 66). `waves` (default) is everything above: each wave is coded, gated, reviewed and committed before the next starts. `graph` needs `execution_mode: per-wave`; with `batch` the run is refused. Under `graph`:
  - A plan starts as soon as the plans it waits for are committed. It waits for its `depends_on`, for any earlier plan whose owns or `files_modified` overlap its own, and for the tracers of earlier waves. A cycle is refused.
  - Each plan then runs alone: its executor and transfer, a gate of only its own obligations (`<waveId>-<plan>-<n>.json`) with fix rounds, then its review, fixer and resolution check. A red plan holds only itself and the plans that wait for it.
  - Ready plans join one commit queue. Each batch runs the repo-wide suite (adapter gates, build, tests; `join-<n>.json`) and is committed on green, one commit per handoff wave in the batch (or per plan with `per-plan`).
  - Suite failures in the batch's files go to fix rounds. Failures only in files of another open plan make the batch wait for that plan, and the two commit together. An obligation that failed only in another open plan's files runs again with that suite.
  - The phase gate at the end is the same as under `waves`.
  - Gates, stray and resume checks and commits never overlap a main-tree writer (shared-tree executor, transfer, fixer). With `isolation: shared`, a gate therefore waits for running executors; `worktree` keeps executors parallel to gates.
  - Reviews across plans are capped by `gsd.code_review.max_concurrent` (default 1). Raise it to review plans in parallel.
  - The result adds `schedule: "graph"`, `order` (start and commit order) and `committed`.
  - One plan's stop leaves the others running to their commit. Its dependants are listed in `skipped` ("blocked by"). The result is the first stop plus `stopped` (every stop).
  - A quota stop, or any failed or refused step, drains the run: plans not committed are listed in `interrupted`.
  - Rerun with the same args to resume. Committed plans are kept, coded plans go straight to their checks, and recorded reviews are reused.

### Results
- `executed`: run `gsd-verify` with `evidence` = the result's evidence list (in `per-wave` that is the one phase gate file). When the result has `skipped`, report those plans first (halted or blocked): the phase is not complete.
- `nothing-to-run`: follow `route` (verify, complete, plan-gaps, uat, stuck: answer the halt named with `ph gsd halt clear`, never "done").
- `needs-owner`: show stage, reason and options. Quota or rate limits never offer retry-now: report the reset time. A Rule-4 or checkpoint result needs the owner's decision; a red tracer wave starts no later wave. A Fix stop whose reason says `last edit unverified` means the fixer's last edit has no build or test run after it: run the failing tests before any hand fix.
- `refused` / `failed`: report the reason. `refused` names the holder: a plan or an execute of this phase (`phase-<NN>` lease), or a debug or quick run on the code root.
