- Read the plans, the summaries (claims, not proof), ROADMAP, REQUIREMENTS, CONTEXT and the gate evidence files listed in your prompt. Do not rerun builds or tests: evidence that is stale or invalid is listed as such, never as proof.
- Write only the VERIFICATION.md path in your prompt, with `covered_files` and `covered_digest` from `gsd_run verification.fingerprint`. Do not commit.
- Per-criterion verify: when your prompt names one success criterion (`SC-<k>`) or the phase-wide checks and a part file under `verify/`, write only that part (the frontmatter of a VERIFICATION report plus the `criterion` and `attempt_key` lines the prompt gives) and judge only that scope; the other criteria have their own verifiers and the run merges the parts into VERIFICATION.md. Your status and score are those of your scope alone.
- Artifacts (Step 4, `gsd_run query verify.artifacts`): each artifact in the JSON carries `status`, one of `passed`, `failed`, `missing`, `directory` or `path_rejected`, and its `issues` are exactly these strings: `file does not exist`, `path is a directory`, `path outside the code root`, `N lines < min_lines M`, `does not contain X`, `does not export X`. Map by `exists` and `issues` as the status table says, whatever the wording: `exists=false` is MISSING, and `exists=true` with any issue is STUB, so a `failed` artifact is never VERIFIED. The phrases `Only N lines` and `Missing pattern` in the Step 4 list above are not emitted by the tool; ignore them.
- Key links (Step 5): read `all_verified` and each link's `status`, not only the exit code. A `pending` link (its source is written by a later wave) exits 0 and is unevaluated, never WIRED. A `pattern_neutralized` link (lookaround, backreference or over 500 characters) is never WIRED and exits 1: report it as unevaluated. An `invalid_entry` link (no `from`, or neither `to` nor `pattern`) is a defect in the PLAN: report it as NOT_WIRED.
