# paseo-kit interfaces

The contracts every module codes against. Written by code-foundation; other coders do not edit this file (file a request, see "Integration requests"). Requirement IDs refer to `.planning/REQUIREMENTS.md`; module numbers to `.planning/intel/SYNTHESIS.md`.

All code: Node.js 24, ES modules (`.mjs`), no npm dependencies, UTF-8 for every file written. Windows first (paths with spaces, CRLF, case-insensitive paths, `.cmd` shims); POSIX paths present.

Installed project layout: `ship/` maps 1:1 onto the project root (`ship/.agents/harness/ph.mjs` -> `<project>/.agents/harness/ph.mjs`). Code under `ship/` must never reach outside `ship/` at run time (INV-09): import only relative paths inside `.agents/harness/`, and never a kit checkout or a path read from the manifest.

Imports between modules (dependency direction M3 <- everything; M4 <- M5 <- M6 <- M10):
- Everybody may import `config.mjs`, `platform.mjs`, `lib/*.mjs`.
- Only `paseo-client/` talks to the daemon or imports `@getpaseo/*` (PCLI-01). `runtime/`, `workflow/`, `gsd/` reach Paseo only through a `Session` (section 6).
- `workflow/` may import `runtime/` exports that code-ph documents (model selection, prompt assembly, agent definitions); code-ph lists them in its integration report.
- Hooks (`.claude/hooks/`) and the file backend import `config.mjs` by the discovery rule of HOOK-04 / CONF-09 (absolute file URL of `<root>/.agents/harness/config.mjs`), never by a relative path into another tree.

## 2. Output and exit conventions (P8)

- One line per item on stdout. An item failure is one line `failed <what>: <err>` and makes the command exit 2 ("done with problems").
- Exit codes: 0 done; 1 usage error, config error or file error (nothing or nothing more done); 2 done with differences, conflicts, failed items or problems. `ph gsd` verbs add 66 (nothing in scope) and 69 (could not look / not ported) (GSDC-02); `ph` returns them unchanged.
- `ph` prints `usage error: <first line, <=300 chars>` for a `UsageError` and `failed: <first line>` for any other thrown error, both exit 1.
- Error text in a line is `errText(e)`: first line of the message, at most 300 characters.
- Non-blocking commands end with the `next:` wait hint (PHCL-07) rendered with `phCommand()` (section 5).
- `kit.mjs` (M1/M2): usage line on stderr + exit 1 for bad arguments; `failed: <msg>` for expected failures, `error: <msg>` for unexpected ones (INST-01, MACH-01).

## 3. Config API (M3): `ship/.agents/harness/config.mjs`

```js
import { loadConfig, loadKitConfig, configProvenance, configRoot, discoverConfigRoot,
         ConfigError, MACHINE_KEYS, KIT_OWNED_KEYS, MERGED_KEYS, DEFAULTS_FILE, OVERLAY_REL, MANIFEST_REL } from "./config.mjs";
```

| export | contract |
| --- | --- |
| `configRoot(env = process.env, cwd = process.cwd())` | `env.PASEO_HARNESS_ROOT` else `cwd`, resolved absolute (CONF-01). |
| `discoverConfigRoot(startDir, env = process.env)` | `env.PASEO_HARNESS_ROOT`, else the nearest ancestor of `startDir` holding `.agents/harness-kit.json` or `.agents/harness.config.json`, else `startDir` (CONF-09; file backend). |
| `loadKitConfig({defaultsFile} = {})` | Defaults alone (`_` keys stripped), closed-validated. Fresh object each call. |
| `loadConfig(root = configRoot(), {defaultsFile} = {})` | Defaults + `<root>/.agents/harness.config.json` overlay, merged (CONF-04) and closed-validated (CONF-05/06). Fresh deep copy each call; the defaults are never mutated. |
| `loadConfigLenient(root, opts)` | `{cfg, error}`: on any overlay error `cfg` = kit defaults and `error` = the `ConfigError` (for `ph doctor`, CONF-08). Defaults errors still throw. |
| `configProvenance(root = configRoot(), {defaultsFile} = {})` | `{defaults: <abs path>, overlay: <abs path>|null, manifest: {version, installedAt, updatedAt}|null, warnings: []}` (CONF-10). |
| `validateConfig(cfg)` | Throws `ConfigError` or returns `cfg` (used by tests and the adapter linter). |
| `mergeOverlay(defaults, overlay)` | Pure merge (CONF-03/04); returns a new object. |
| `ConfigError` | `extends Error`; `message` is `invalid harness config <dotted.key>: <msg>` (or `invalid harness key <key>` for `__proto__`/`constructor`/`prototype`); `.key` holds the dotted key. |
| `MACHINE_KEYS` | `agent_providers`, `agent_provider_disallowed_tools`, `agent_provider_env`, `main_provider_disallowed_tools`. |
| `KIT_OWNED_KEYS` | `MACHINE_KEYS` + `first_prompt_note`: overlay values are ignored silently (CONF-03, CONF-14). |
| `MERGED_KEYS` | `tiers`, `tier_aliases`, `platform_notes`, `context_guard`, `io_guard`, `read_limits`, `adapter`, `gsd`: one-level per-entry merge (an overlay entry replaces that whole entry); every other key is replaced wholesale. |
| `DEFAULTS_FILE` | absolute path of `.agents/harness.defaults.json` next to `config.mjs`. |
| `OVERLAY_REL` / `MANIFEST_REL` | `.agents/harness.config.json` / `.agents/harness-kit.json`. |
| `GSD_ROLES`, `THINKING_LEVELS` | re-exported from `lib/config-schema.mjs` (section 4). |

Rules:
- No consumer embeds a default value or opens `harness.defaults.json` / `harness.config.json` itself (CONF-12). `.claude/harness.config.json` and `.planning/config.json` are never read (CONF-07, CONF-13).
- Overlay errors: not an object -> `invalid harness config overlay: expected an object`; unparsable -> `invalid harness config overlay: invalid JSON (<parser message>)`.
- Overlay keys starting with `_` are ignored at the top level only.
- A key another module needs is added to the schema by code-foundation first (file a request); never add keys from another module's code.

## 7. Paseo client (M4): `ship/.agents/harness/paseo-client/index.mjs`

The only module that talks to the Paseo daemon (PCLI-01). It loads the npm-installed Paseo CLI's own client (`dist/utils/client.js` -> `connectToDaemon`, `dist/commands/agent/run.js` -> `resolveStructuredResponseMessage`) from the CLI directory (PCLI-02) and connects to `$PASEO_HOST`, else `daemon.listen` of `<paseoHome>/config.json` (PCLI-03; never `paseo.pid`). Everything else goes through a `Session`.

```js
import { connect, TESTED_PASEO_CLI, PARENT_LABEL, READ_ONLY_DENIED_TOOLS, clampThinking,
         assertPromptSize, findCliDir, daemonTarget, UsageTracker, filePluginState, pluginEnv } from "../paseo-client/index.mjs";
const session = await connect({ env, root, cfg, clock });   // or ctx.paseo() inside a ph command
```

`connect({env = process.env, root = configRoot(env), cfg = loadConfig(root), clock = realClock, daemon} = {})` -> `Promise<Session>`. `daemon` (tests only) is `{connect(): Promise<{client, version, cliDir, reply, capabilities}>}` (the fake's `fake.daemon`); without it the real CLI is located and connected. Connection failure throws the CLI's `Cannot connect to daemon at ...` message (callers print it as `failed: ...` / doctor `problem paseo: ...`).

## 8. `ph` entry and command registry: `ship/.agents/harness/ph.mjs`

`node .agents/harness/ph.mjs <command> [args]`. `ph.mjs` owns parsing of the command name, `help`, `config`, error printing and exit codes; every other command lives in a command module owned by its coder.

Command modules (fixed list in `ph.mjs`, imported in this order; a module file that does not exist is skipped, any other import error fails `ph`):

| module | owner | commands (examples) |
| --- | --- | --- |
| `./runtime/commands.mjs` | code-ph | doctor, spawn, fanout, send, watch, result, team, context, compact-self (+ hidden watcher), stop, archive, task, freeze, worktrees |

Each module exports `commands`, an array of command definitions:

```js
export const commands = [{
  name: "spawn",                      // first argv token; unique across all modules (duplicate -> ph fails)
  summary: "start named agents and return at once",   // one line in `ph help`
  usage: "ph spawn --name N (--prompt T | --prompt-file F) [--count K] ...",  // shown by `ph help <command>`
  options: { name: "string", count: "string", prompt: "string", "prompt-file": "string", "read-only": "bool" },
                                      // parsed by ph with parseArgs (PHCL-02); null = the handler gets raw argv (e.g. `gsd`),
                                      // which answers -h and --help itself; for a parsed command ph prints `usage` (G153)
  config: "required",                 // "required": invalid config -> `failed: invalid harness config ...` exit 1 (CONF-08)
                                      // "lenient": ctx.cfg = defaults and ctx.configError = the error (doctor only)
                                      // "none": no config load
  hidden: false,                      // true: not listed by help (internal commands such as the compact watcher)
  run: async (ctx) => 0,              // returns the exit code (undefined = 0); throw UsageError for usage errors
}];
```

Handler context `ctx`:

| field | meaning |
| --- | --- |
| `name` | the command name. |
| `argv` | raw tokens after the command name. |
| `opts`, `args` | parsed options and positional tokens (when `options` is not null). |
| `env` | the environment to use (never read `process.env` in a handler; tests pass their own). |
| `root` | `configRoot(env)`. |
| `cfg`, `configError` | effective config (`null` for `config: "none"`); `configError` only for `"lenient"`. |
| `out(line)`, `err(line)` | write one line (newline added) to stdout / stderr. |
| `write(text)` | raw stdout write (pass-through output). |
| `clock` | the clock (section 5). |
| `paseo()` | `Promise<Session>`: connects once on first call with `{env, root, cfg, clock}`; ph closes it in `finally`. |
| `ph` | `phCommand()` (for `next:` hints and teammate notes). |

Exit mapping in `main`: handler return value as is (0, 1, 2, 66, 69); `UsageError` -> `usage error: <msg>` exit 1; other error -> `failed: <msg>` exit 1.

Built-ins in `ph.mjs`: `help` / `--help` / `-h` / no command (usage + public command list, exit 0), unknown command (same text, exit 1), `<command> -h` / `--help` for a parsed command (its `usage` and summary, exit 0, the command does not run; G153), `config` (CONF-10: effective config as 2-space JSON with `_provenance`, exit 0; invalid config -> `failed: ...` exit 1).

`main(argv, {env = process.env, cwd = process.cwd(), out, err, write, clock, daemon} = {})` is exported for in-process tests (`daemon` is passed to `connect`; `ctx.root` = `configRoot(env, cwd)`). Error lines (`usage error:`, `failed:`) go to stderr; everything else to stdout. Run as a script, `ph.mjs` sets `process.exitCode = await main(process.argv.slice(2))`.

## 11. Review integration contracts (2026-10-20)

### Creation, deadlines and worktrees

- A post-creation usage-tracking error carries `{agentId, archived, archiveError}` and `cause` (the tracking error). `archived` is a confirmation boolean, not the truthiness of the error. The message says `(archived)` only after confirmation; otherwise it names the possible live agent and cleanup failure. Creation callers preserve that agent's worktree and capacity accounting until cleanup is confirmed.
- `waitTurn.deadline` is absolute milliseconds on `session.clock`. Waits and late-usage settling are capped to it; backoff and permission handling check expiry before sending anything else, and late waits/replies cannot succeed. `UsageTracker.settleTurn(agentId, turnsBefore, lastUsage, deadline = Infinity)` preserves exactly-once usage accounting within that allowance. Workflow `timeoutS` spans all turns/retries, with `no reply within <timeoutS> s`; in-flight RPC completion still depends on the client transport.
- Workflow `agent()` additionally accepts `detail`, `timeoutS`, and `worktreeSeed`. `detail` returns `{result, reason, agentId, worktree, durationS}`; `worktree` is the path even on cached non-session calls. The `runId` script global is the original run of the resume chain.
- `worktreeSeed: {head, files: [{path, sha256} | {path, deleted: true}]}` is a runtime-owned accepted-dependency input for worktree isolation and is included in the cache key. The runtime validates HEAD, source identities, contained paths and absence of links before copying. It records the seed in the new worktree's git directory (`harness-seed.json`) before dispatch. Failures discard only that newly created tree. Session continuations reuse their tree, not reseed it.
- GSD batch executors obtain seeds only from earlier accepted transfer records. Transfer compares the worker against both HEAD and the recorded seed: unchanged dependencies are excluded, but modifying a seed or restoring it to HEAD is still a worker change subject to owns/deletion checks. Owned pre-execution dirty files remain refused; immutable content-addressed planning/skill/config snapshots supply uncommitted planning inputs.

### Adapter and evidence

- `adapter/contract.mjs`: async `gateObligation(cfg, {codeRoot, phaseDir, kind, command, target})` returns `{outcome: ready|unavailable|not_configured, kind, argument, targets, argv, timeoutS, exitCodeSufficient, evidenceParser, reason}`. Parser failure supplies no executable argv. An empty target set for a kind that is not `exit_code_sufficient` is `unavailable` with reason `no concrete targets selected`. The default parser uses the trimmed argument; `{argument}` and `{targets}` are substituted before spawning.
- `adapter/evidence.mjs`: async `requiredSteps(cfg, {codeRoot, phaseDir, plans})` supplies the independent expected step set; `gateStepName` and `obligationStepName` share names between writer and reader; `executionProblem({targets, executed, exitCodeSufficient})` enforces nonzero execution/target coverage. A passed step must have exitCode 0 and an existing log; executed is `{count: number|null, targets: []}`.
- `flow-gate.mjs` `evidenceCheck` is async. Evidence captures inputs before the commands and rejects mutation during them. `inputs.scopes` records patterns for rescanning additions/deletions; `inputs.config` hashes effective adapter/gsd values from loadConfig. Missing-file identities and HEAD are checked. Null build/test produce `not_configured` steps, never green evidence.
- Hook requests/responses are closed shapes, nested records included. Exactly one nonblank stdout JSON line is accepted. Resolve must answer every requested target exactly once; shared may return only requested paths; attribute answers every failure once with a requested plan id or null. Unknown request fields throw; invalid responses become unresolvable.
- `adapter/mutex.mjs`: `tryLock(name, {tmp}) -> token|null`, `unlock(name, token, {tmp})`. A rename publishes `{pid, token}` ownership; stale recovery is serialized by a per-lock reap claim and release checks ownership. `acquireMutex(name, {log, clock, tmp})` waits and returns the release; `withMutex` reports waiting once. `runtime/cap-lock.mjs` `takeCapLock(root, caller, clock)` is the caller-wide agent cap lock (`_workspace/locks`, one per caller) that spawn, fanout, collect and each workflow call take around their count and create of agents.

### Adapter generation identity self-check

- Parser targets are canonical execution identities. Resolve validates those exact IDs, one result each; it cannot expand or rename them. File/suite aliases either expand in parse before runner argv substitution, or remain selectors only when completed runner records prove the selector's membership and completion. Request echoing, nonzero counts alone and discovery-only mappings are not execution proof. Skipped cases do not count.
- `adapter/check.mjs` exports `checkObligation(cfg, {codeRoot, kind, command, outputDir?, execute: true})`. Explicit opt-in runs the existing parse/resolve/runner/evidence protocol under the adapter mutex and uses unchanged `executionProblem`; no new config keys or hook fields. Returns a retained transcript `{v, kind, command, outcome, reason, directory, obligation?, resolve?, runner?, evidence?}`. Non-ok resolution stops before running; empty targets for non-exit-code-sufficient kinds, failed runners, failed evidence and incomplete coverage are rejected.
- Standalone CLI: `node .agents/harness/adapter/check.mjs --kind <kind> --command "<obligation>" --run [--output <dir>]`, from the project root (or `PASEO_HARNESS_ROOT`). Exit 0 passed, 2 rejected, 1 usage/config/error. Each call creates a fresh directory with `check.json` and runner logs under `_workspace/adapter-check/` by default. It executes project code only with `--run`; lint remains structural. This is not full gate evidence or a security boundary against a dishonest project hook.
- Generation readiness requires independent expected-ID/count assertions across every supported selector form (single, multi-test file, suite alias), plus rejection of zero execution, missing coverage, failed runner and unknown selector. Preserve real positive logs and labeled isolated negative controls; unavailable checks mean not ready. The kit overlay specifies this self-check without changing protected Harness/GSD method text.

### GSD diagnostics and durable flow records

- `gsd/upstream.mjs`: async `checkTarget(target) -> {problems, warnings, references, verbs, verbose}` is read-only and independent of project configuration. Doctor uses the selected root even when its overlay is invalid. Kit GSD namespaces remain inventoried; arbitrary project role files alongside them are allowed.
- `gsd/draft.mjs` `validateDraft` is shared by pre-approval checks and `roadmap install-draft` inside the single-writer lock. It requires nonempty categorized v1 coverage, exactly one matching phase per expected ID, no extra IDs, valid roadmap grammar and 2–5 criteria per phase before shared files change.
- `execute-progress.json` distinguishes coding SUMMARYs, commits and STATE tracking. A resumed partial transaction reruns required gates/reviews. Required code commits and record writes must succeed before tracking; wave/override writes must succeed before proceeding.
- Pending cross-plan requests persist until fix replies explicitly acknowledge them in `resolvedRequests`. Fatal failures and owner decisions stop the fix round. Missing review judgments, unknown severities and quick verification without a fresh passing artifact fail closed.
- Plan, execute, debug and quick acquire the same root writer lock. Acquire/reap/release use an exclusive transition claim, live host PID and owner token (not run-id equality). Interrupted transition claims fail closed and may require manual recovery.
- Map-codebase acquires its own `codebase-map` lease for the whole run (not the debug one, so plan and execute keep pipelining); a second map on the same root is refused. The stamp refuses when HEAD moved since the mappers were dispatched (a commit landed during the map).
- Verify acquires a per-phase lock `verify-<NN>` from its attempt record through readback and routing, not the root writer lock; a second verify of the same phase returns `refused` while the first runs.
- Research acquires a per-phase lock `research-<NN>` from its status check through readback, not the root writer lock; a second research of the same phase returns `refused` while the first runs. `revisions record` reads, merges and writes `revisions.json` under `revisions.json.lock` (the STATE.md lock rules), so concurrent records keep each other's keys.
